# 研发迭代方式与 2026-10-16 记录

每轮按失败证据推进：复现问题、写回归、改实现、跑真实模型、使用模型工作区外的固定
测试台独立核验。保留失败结果；不以合成模型回复、单测通过或独立验收替代真实自主闭环。
开发 API 为 Qwen3.8-27B，最终 GGUF/R9700 离线验收仍是单独的未完成项。

## 本轮已修复的缺陷

1. 时序测试采样竞争：旧模型 TB 在 posedge 后立即比较，对正确 FIFO 报 26 个错误。
   保持 RTL/预期不变，只延迟到 NBA 更新后，50 次检查通过。技能现要求非有效沿驱动、
   NBA 后采样。证据在 `../out/` 的对应 trace 和 `../../trusted-evaluation/fifo-race-*-20261016/`。
2. 通用 TB 框架：模型可只提供 declarations/stimulus/checks；工具生成 token、watchdog、
   检查计数和覆盖标记。框架不生成 DUT 答案或预期值；model oracle 的正确性仍需独立评测。
3. 片段作用域：刺激放入独立 begin 块，局部变量可位于块首，不受框架 token 语句影响。
   驱动信号的 reg/logic 类型及先声明后实例化已写入说明。
4. 检查标签：额外用例标签允许存在，但不能替代任一必需覆盖组。零比较、漏组、错误 DUT
   均被真实 Vivado 负向验收拒绝。
5. 观察遗忘：保留近期 assistant/tool 对，包括不同文件及同一文件的不同窗口；给模型压缩级联诊断，
   原始日志不删减。tb_error 直接附带当前模型生成的 TB 和修复提示。
6. 修复成本：工具确认 TB 错误后，amend_test 支持唯一 old/new 补丁，保留完整内容模式。
   仍禁止通过修订 TB 清除 DUT 反例；冻结、版本哈希和证据失效逻辑继续生效。
7. 模型调用重试：下一轮包含上一轮解析错误，便于模型按函数定义纠正调用。

## 测试入口

```powershell
python tools/serve_development.py --code-first --reasoning-effort low
```

模型通过原生函数调用选择工具；通用仿真框架可选完整 TB 或片段，后续工具由模型选择，
没有固定修复轮数。累计 token 用量仅记录；单轮输出按配置上限和实际上下文余量分配。
按实测回复速度和剩余时间提供软长度建议，为工具预留时间，不修改请求的硬 token 上限。

历史阶段上下文实验及其请求保存在各次运行档案中，未证明解决 FIFO 超时。
单轮 8192 只作过配置对照，当前测试额度按启动参数设置。

## 性能定位与后续验收

离线回放 6862 个生产风格 SSE 记录仅 2.38 s。FIFO 前五次首个增量约 3-5 s 到达，
03/04/05 的首轮推理阶段持续约 220 s；主要时间消耗在模型推理输出，不能只归因于日志写盘。
统计在 `../out/development-20261016/latency-profile.json`。这不等同于实测服务端 GPU 吞吐。

尚未达到 FIFO 300 秒自主测试和提交的验收目标。近期记忆及补丁路径已单测，
但未证明真实模型可在期限内修复该 FIFO TB；不要把可信侧人工定位修复算作模型成功。
后续重点是固定推理环境和案例集，验证可控的非思考/低推理配置、有限测试生成及真实修复。
本机只读发现 RTX 5060 Laptop/Intel GPU，已有下载是 Linux ROCm 运行库；当前未验证本机
可运行最终 GGUF，也没有以 Windows 结果代替最终 R9700 离线验收。

可信评测统一入口 `../../trusted-evaluation/judge_public.py`，使用固定外部 TB 与真实
Vivado 编译、展开、仿真、ZU3EG OOC 综合；不使用第三方 RTL 判定器。

由于当前目录没有 Git，后续实验先使用 `python tools/snapshot.py --out out/<trial>/snapshot`

包括开发测试源文件，不是生产提交镜像；生产镜像继续按 Docker 白名单排除测试/评测资料。

## 2026-10-17：转向真实修复能力

以下记录对应当时的协议对照实验，配置以档案中的完整请求为准。
AMD 云 API 探测 3.44 s 返回完整函数调用；AND 在 50.53 s 完成保存/自测/提交，
独立四组合仿真与综合通过。相同 FIFO 的原生模式 299.19 s 超时，工具执行 0 次、
没有 RTL；模型仍在首轮推理中规划完整测试台。相比默认 JSON 的既有结果并无改善，
后续修复评估恢复 JSON 协议。记录在 `../out/development-native-20261016/`
和 `../out/dev-loop-native-{and,fifo}-20261016-01/`。

闭环现在持续保存 `state.pending_counterexample`：包含失败候选哈希、测试台哈希、
实际 expected/actual 诊断及日志路径。读取文件、修改代码和编译 PASS 都不会解除反例；
只有修改后的候选在相同测试台复验 PASS 才解除。相同失败候选偶然重跑 PASS 仍保留反例。
回归验证了这些行为，避免近期观察被后续动作覆盖后丢失具体错误。

真实修复评估使用公开规格与有缺陷的开发草稿：先原样保存草稿，再让模型自行产生
测试、观察失败、修改 DUT，并重跑原测试。隐藏的独立测试台仅用于可信侧验收。
该评估区分“自行修复”与“初次生成正确”，不会把脚本测试或研发手动修复算作模型成功。

修复练习首测实际遇到 TB 片段多写 `initial begin/end`，触发 VRFC 10-4982/10-8549。
适配器现在将片段开头的 `initial begin` 转成内部 `begin` 块，保留所有刺激、
循环及比较，不删除 begin/end 内容；其余构造不重写，转换写入 trace。
可信侧将原始模型片段仅作这一转换、保持原有缺陷 DUT 与期望不变后，Vivado 编译/
展开通过，并在 `sat1` 比较失败。复现在 `../../trusted-evaluation/repair-counter-wrapper-repro-20261017/`。
这证明适配修复暴露了真实 DUT 故障，并不等同于模型已完成 DUT 修复。

同题第二次真实云 API 运行在 162.15 s、5 轮内完成：原样保存有缺陷草稿 →
自建 TB 发现饱和回绕故障 → patch_file 修复 DUT → 同一 TB 的 5 次比较通过 → submit。
失败/成功测试台 SHA-256 完全一致；调用 3、4 的状态持续带有反例，调用 5 才解除。
该次模型未生成多余 initial 包装，故不能将其成功归因于包装兼容修复。
记录在 `../out/dev-loop-repair-counter-20261017-02/`。
独立冻结 TB 的 22 次比较及 Vivado ZU3EG 综合通过（LUT=4、FF=4）；可信侧结果在
`../../trusted-evaluation/dev-loop-repair-counter-20261017-02/result.json`。
完整回归 75 项通过；该单次修复成功不证明总体正确率，也不代表 FIFO 时限问题已解决。
